# light-server 設計書

状態: 設計レビュー用。実装開始前のユーザー確認待ち。

## 目的

Codexなどで作った成果物を、プロジェクトごとにサーバーを起動せずに閲覧・操作できるようにする。1つの常駐サーバーが、静的ファイルの配信、JSONオブジェクトのCRUDと簡単な検索、バイナリのアップロード・ダウンロードを提供する。

作業場所 `/mnt/ssd01/project/light-server` は調査時点で空で、Gitリポジトリでもない。既存実装・既存の言語制約はない。この設計書以外の実装やセットアップはまだ行わない。

## ユーザーと合意した要件

- 最初は自分用。別端末からはSSHのポート転送で利用する。
- Goで実装する。サーバーと管理CLIを同じ実行ファイルにまとめる。
- systemdで常駐し、OS起動後に自動起動、異常終了時に再起動する。
- 待ち受けは `127.0.0.1` を基本にする。
- 管理はCLIとHTTP API。ブラウザの管理画面は作らない。
- 静的配信は既存フォルダを名前付きで登録する方式を基本にする。
- 公開内容を固定したい場合は、Codexなどが共通の配信フォルダにコピーし、そのフォルダを登録する。サーバー専用の公開・コピー機能は不要。
- JSONとアップロードされたバイナリは、そのプロジェクトに帰属する。
- 各プロジェクトの保存フォルダに、登録情報、SQLiteファイル1つ、バイナリ保存ディレクトリをまとめる。配信元フォルダとは分ける。
- JSONは種類名（コレクション）とIDで管理する。事前のスキーマ定義は不要。
- JSONはCRUD・一覧、項目の一致検索、文字列の部分一致検索、並べ替え、取得件数指定に対応する。
- APIはCodexなどのコマンドからも、配信ページのJavaScriptからも利用できる。
- プロジェクトごとにAPIと保存先を分ける。別プロジェクトへのアクセスを認証で拒否する仕組みは当面設けない。
- データは再起動後も保持し、明示的に削除するまで残す。バックアップは対象外。
- 配信登録の解除では保存データを削除しない。完全削除は別操作にする。
- 大容量ファイルはストリーミングで転送する。ダウンロードのRangeと動画のシークに対応する。アップロードの途中再開は初期版では行わない。

## 検討した方式と選定

### 配信元

1. 共通フォルダへコピー: 公開内容を固定しやすく、作業元を削除しても残る。一方でコピー、反映忘れ、容量の二重使用が発生する。
2. 既存フォルダの直接登録: 編集を即反映でき、大容量成果物を複製しなくてよい。一方で編集途中も見え、移動・削除で配信できなくなる。

直接登録を基本に、必要な場合のみ利用者側でコピーする方式を選定した。

### JSON保存

1. プロジェクトごとのSQLite: 検索・並べ替え・更新を一貫して処理でき、別のDBサーバーが不要。直接見るにはSQLite対応ツールが必要。
2. オブジェクトごとのJSONファイル: エディタで読み書きできるが、検索時の走査、同時更新、書き込み中断への対処を別途作る必要がある。

プロジェクトごとのSQLiteを選定した。バイナリ本体はDBに入れず、通常のファイルとして保存する。

参考: SQLite公式「Appropriate Uses For SQLite」 https://www.sqlite.org/whentouse.html

## 構成案

以降のパス、コマンド名、APIの細かな振る舞いは設計側の提案であり、ユーザーが個別に指定した仕様ではない。目的と合意要件を変えない範囲の実装判断は実装者に委ねる。

```text
保存ルート/
  projects/
    project-a/
      project.json
      data.sqlite
      files/
    project-b/
      project.json
      data.sqlite
      files/

配信元の例（保存ルート外でもよい）/
  review-output/
    index.html
    assets/
```

`project.json` はプロジェクトID、配信元の絶対パス、登録状態などを持つ。SQLiteのWAL・共有メモリなどの補助ファイルやアップロード一時ファイルも、そのプロジェクトの保存フォルダ内に置く。

保存ルートの既定値はXDGのユーザーデータディレクトリ配下の `light-server` とし、サーバー起動時のオプションで変更できる。ポートは設定可能とし、既定値は実装時に空き状況を確認して選ぶ。1つの保存ルートを複数サーバープロセスが同時管理する運用は対象外とし、ロックで二重起動を検出する。

### 配信とプロジェクトの生存期間

- `/p/{project}/` から登録フォルダを静的配信する。
- `/api/projects/{project}/...` から同じプロジェクトのデータを操作する。
- CLIは登録時に閲覧URLとAPIの基点を返す。ページはプロジェクト固有のAPI基点を利用する。
- 配信元フォルダが存在しなくなった場合、静的配信は失敗するが、保存済みデータは消えない。
- 登録解除はプロジェクトを非アクティブにする。静的配信とデータAPIを停止し、保存フォルダは維持する。CLIから保持済みの一覧・再登録が可能。
- 同じIDの再登録で保持データを再利用できる。アクティブなIDの重複登録はエラーとし、配信元変更は明示的な更新操作にする。
- 完全削除は対象IDを明示する独立した操作にする。削除対象はサーバー管理下のプロジェクト保存フォルダであり、登録した配信元フォルダは削除しない。
- 保存ルートを静的配信元に指定することは拒否する。静的配信から保存データを直接閲覧できる構成は作らない。

静的サイトは `/p/{project}/` 配下で動く相対URL・ベースパスに対応している必要がある。ルート絶対URLの自動書き換え、任意の開発サーバーの代理起動・リバースプロキシ、SSRは対象外。初期版は通常のファイル配信とし、SPA向けの一律index.htmlフォールバックは行わない。

### JSON API

想定する形:

```text
GET    /api/projects/{project}/collections
POST   /api/projects/{project}/collections/{collection}/objects
GET    /api/projects/{project}/collections/{collection}/objects
GET    /api/projects/{project}/collections/{collection}/objects/{id}
PUT    /api/projects/{project}/collections/{collection}/objects/{id}
DELETE /api/projects/{project}/collections/{collection}/objects/{id}
POST   /api/projects/{project}/collections/{collection}/search
```

- コレクションは最初の保存で自動作成する。
- 保存する本文はJSONオブジェクト。配列やスカラーだけの本文は受け付けない。
- POSTはサーバー生成IDで新規作成、PUTは指定IDの作成または全置換とする。部分更新・版管理は初期版では行わない。
- 同じオブジェクトへの更新は最後に成功した書き込みを採用する。検索・読み取りから書き込み途中の本文が見えないようトランザクションを使う。
- 作成日時・更新日時・IDは利用者のJSON本文と分けたメタデータとして管理する。
- 一致検索はトップレベルの項目名と型付きの値で指定する。文字列の部分一致はワイルドカード式ではなく文字通りの部分一致とする。複数条件はAND。
- ネストした項目へのパス指定、全文検索、任意SQL、OR式・集計・JOINは初期版の対象外。
- 並べ替えは指定したトップレベルの項目またはメタデータ1項目と昇順・降順。未指定時もIDなどで順序を確定する。同値時の順序もIDで安定させる。
- `limit` と `offset` を設ける。既定値・上限・混在型や欠落項目の並び順は実装時に定義して文書化する。
- 不正なJSON・検索条件には400、不在には404、競合する新規登録には409を返す。エラー本文の形式を統一する。
- SQLの値はパラメーターで渡す。項目名も検証し、利用者のSQL断片を受け付けない。

### バイナリ API

```text
GET    /api/projects/{project}/files
PUT    /api/projects/{project}/files/{key}
GET    /api/projects/{project}/files/{key}
HEAD   /api/projects/{project}/files/{key}
DELETE /api/projects/{project}/files/{key}
```

- ファイルはプロジェクト内のキーで指定する。キーは安全な単一パス要素とし、拡張子付きの名前も使える。ディレクトリ階層は初期版では扱わない。
- PUTはリクエスト本文をストリーミングで受け、同じキーなら置換する。
- 受信途中は一時ファイルへ保存し、完了後に置換する。中断やディスク不足で既存ファイルを壊さず、不完全なアップロードを公開しない。一時ファイルを回収する。
- GET/HEADはContent-Length、Content-Type、Rangeに対応する。通常のファイルとしてシークでき、無効なRangeは適切に拒否する。
- Content-Typeはキーの拡張子と必要な範囲の内容判定から決め、不明なら `application/octet-stream` にする。
- 一覧はキー・サイズなどを返し、本文を読まずに処理する。ページング可能にする。
- バイナリのURLまたはキーをJSON本文に保存できる。参照整合性や未参照ファイルの自動削除は行わない。
- ファイル全体のメモリ展開を避ける。上限値やタイムアウトは大容量転送を考慮して実装し、設定方法を文書化する。

### CLIとAPIの関係

```text
light-server serve
light-server project add <id> --dir <absolute-path>
light-server project list [--all]
light-server project update <id> --dir <absolute-path>
light-server project remove <id>
light-server project purge <id>
```

管理CLIは稼働中サーバーのHTTP APIを呼ぶ。登録・解除・完全削除など、CLIでできる管理操作には対応する管理APIを用意する。CLIだけが直接ファイルやDBを書き換える構成にはしない。サーバー未起動時は接続失敗を明示する。

初期版のデータ操作は文書化したHTTP APIを `curl` などから呼べればよい。全CRUD・検索・転送を包む専用CLIやブラウザSDKは必須にしない。登録とURL取得、JSONの作成・検索、バイナリの送受信について、そのまま使えるCLI・JavaScript例を用意する。

### 常駐とアクセス範囲

- systemdで常駐し、SSH切断後も動く構成にする。
- ユーザーサービス＋lingerを第一候補とする。インストール時に権限とOS起動後の実行条件を確認し、必要なら適切なユーザー権限で動くシステムサービスを選ぶ。単にログイン後にしか起動しない状態を「OS起動時から自動起動」と報告しない。
- 作業ディレクトリに依存しない絶対パスで起動する。設定・保存先を永続化する。
- localhostへのSSHポート転送を利用例として記載する。TLS、インターネット公開、ログイン、プロジェクトごとの権限分離は対象外。
- 通常は同一オリジンで使い、広範なCORS許可は設けない。プロジェクトをまたぐアクセス拒否は実装しない。
- 信頼できる自分の成果物を配信する前提。ただしパストラバーサルによる保存先外への読み書きなど、APIの名前とファイルパスを混同する不具合は防ぐ。静的配信でも配信元外を参照するシンボリックリンクの扱いを明示し、保存フォルダへ抜けられないようにする。
- 最低限、起動設定、HTTPの結果、登録操作、ストレージエラーをログに出す。JSON本文やバイナリ内容は通常ログに出さない。

## 初期版で行わないこと

バックアップ、認証・認可、管理画面、アップロード途中再開、DBサーバーの別プロセス、プロジェクトごとのサーバー起動、コンテナ必須化、自動ビルド・ホットリロード機構、公開スナップショットの自動作成、JSONとバイナリをまたぐトランザクション、履歴管理。

## 検証方針

実装時には、以下を実行して結果を確認する。設計時点では未実施。

- 同じサーバーに2プロジェクトを登録し、静的ページを開けること。
- 各ページから自プロジェクトのJSONの作成・読み取り・置換・削除・検索・並べ替えができ、同じコレクション名・IDでも他プロジェクトと混ざらないこと。
- バイナリの送受信、内容の一致、HEAD、Range、動画のシーク、大容量転送中のメモリ使用を確認すること。
- アップロード中断や失敗で既存ファイルが壊れず、不完全なファイルが見えないこと。
- プロセス再起動後も登録・JSON・バイナリが残ること。登録解除・再登録でデータを再利用できること。
- 完全削除の対象がサーバー管理下のデータだけで、配信元フォルダには影響しないこと。
- プロジェクトID・ファイルキー等から保存先の外へ抜けられないこと。
- CLIの登録結果にあるURLでブラウザから実際にページを開き、JavaScriptから読み書きできること。
- systemd設定と稼働状態、localhostの待ち受け、SSH切断後の生存、自動起動の条件を確認すること。再起動試験をしていなければ、その事実を明記する。
